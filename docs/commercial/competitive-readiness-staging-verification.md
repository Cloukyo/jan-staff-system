# Competitive readiness staging verification

## Scope

Use only the documented Commercial Staging Supabase project. Never run this procedure against Jan Production or Commercial Production.

Required application secret: `DBS_REFERENCE_ENCRYPTION_KEY`, a randomly generated 32-byte value encoded as base64. Store it only in the server-side Commercial Staging and later Commercial Production environments. Never prefix it with `NEXT_PUBLIC_` and never store it in the database.

## Pre-application checks

1. Confirm project identity from the documented project reference and Supabase project metadata.
2. Confirm the remote migration ledger exactly matches repository history up to the previous endpoint.
3. Confirm no genuine customer data is present.
4. Capture the current staff, central-record, leave and payroll schema definitions relevant to this migration.

## Synthetic scenarios A to G

| Case | Scenario | Expected result |
| --- | --- | --- |
| A | Employee with a verified enhanced children's barred-list check, full protected reference, suitability decision and start authorisation | Derived recruitment readiness is ready; rota assignment and kiosk enablement succeed. |
| B | Record differs only by normal editing after verification | Original verification decision timestamps remain unchanged; an audit event records a real state change only. |
| C | Required check is missing, pending or lacks receipt/reference evidence | Start remains blocked; rota assignment and kiosk enablement reject atomically. |
| D | Volunteer recorded under the supervised occasional-volunteer exception | The exception is visible and auditable; ordinary volunteer classification alone does not bypass the guard. |
| E | Cross-tenant manager attempts to read or change recruitment, retention or export-audit data | RLS rejects or returns no rows; no state changes. |
| F | Applicable leave or holiday-pay evidence is deleted before six years, or while a hold is active | Database rejects deletion and original evidence remains intact. |
| G | Evidence exports are generated by an authorised manager | Correct tenant rows are exported, sensitive DBS plaintext is decrypted only server-side, and a digest/actor audit row is inserted only after successful generation. |

## Post-application checks

1. Confirm the ledger ends at `20260904031657_nursery_staff_competitive_readiness`.
2. Run schema lint, migration verification, RLS/security tests and focused regression tests.
3. Deploy the exact candidate SHA to Commercial Staging only.
4. Run readiness and liveness smoke checks and record the deployed SHA.
5. Confirm no Production or Jan environment was mutated.

## Forward rollback

Do not delete migration-ledger rows. If rollback is required, create a reviewed forward migration that removes only the new triggers, view, RPC, tables, columns and enum types after preserving any evidence already written. Because retained statutory evidence may exist, obtain explicit data-retention approval before dropping or transforming those records.
